    How it holds up

    Three things that make the rest possible.

    01

    The keys never leave your phone

    Encryption keys are generated inside the Android Keystore — hardware-backed on most devices — and are never handed out to the app, to us, or to anyone else. There is no export function because there is nothing to export.

    Copy the app's data to another phone and it is inert. The files are there. The keys are not.

    02

    Even the backup is unreadable

    Cloud backup uploads a file that was already encrypted on your phone with a passphrase only you know. Google stores it. Google cannot read it.

    There is no FileWall server in the path. There is no account. Nothing is sent to us because there is no us to send it to.

    03

    Nothing on disk says what anything is

    Names, types and folders live only in the app's private database. The stored files themselves have no names and no extensions.

    A file browser with access to that directory sees a pile of opaque blobs — not a holiday album, not a folder marked "Documents".

    How the encryption works

    The details, since you'll want them.

    This is the whole scheme. If something here looks like a trade-off, it is one — the reasoning is at the bottom.

    AES-256

    Keys generated in, and confined to, the Keystore

    File keys are created inside the Android Keystore and never leave it. Encryption happens by handing data to the Keystore, not by handing the key to the app.

    MAC

    Encrypt-then-MAC with HMAC-SHA256

    Every file carries a MAC computed over the ciphertext. A tampered file is detected as tampered rather than decrypted into something unexpected.

    VERIFY

    Integrity is checked first

    The MAC is verified before anything is decoded, rendered, or handed to another app. Nothing downstream ever sees unverified bytes.

    PBKDF2

    Passcodes and backup passphrases

    Passcodes are stored as PBKDF2-HMAC-SHA256 with 120,000 iterations and a random salt. Backup archives are keyed with PBKDF2-HMAC-SHA256 at 210,000 iterations.

    Why CTR and a separate MAC, rather than GCM

    GCM will not release verified plaintext until it has buffered the whole message, which for a video would mean holding the entire file in RAM. CTR streams in constant memory and can be seeked, so scrubbing a two-gigabyte video works without decrypting the two gigabytes before it. The trailing HMAC-SHA256 supplies the integrity GCM would have given us, and it is verified before any of that plaintext is used.

    Honest limits

    What FileWall can't do for you.

    Every one of these is a consequence of a decision made earlier on this page. None of them are going to be quietly fixed.

    01 Forget the backup passphrase and the archive is gone

    There is no reset link and no recovery flow, because there is nobody holding a second copy of your key. An archive whose passphrase is lost is unrecoverable. That is the point of it.

    02 No security audit has been done

    FileWall has not been independently audited or certified. The design is described in full above and the source is public, so you can read it, or have someone you trust read it. That is what we can offer today.

    03 Android today, whatever the roadmap says

    What you can install right now is the Android app and its watch companion. iOS, watchOS, visionOS, Android XR, CarPlay, Android Auto and a web client are being worked on and none of them exist yet. Plan around the Android app; treat the rest as intentions.

    04 Drive backup needs your own OAuth client

    Google Drive backup uses a Google Cloud OAuth client that you create — a one-time setup. It is the cost of having no FileWall server in the middle: your backups go through your credentials, not ours.
